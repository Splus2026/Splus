# Автоматические проверки Синевы+

Запуск из КОРНЯ проекта (рядом с `sp.py`):

    python tests/run_all.py                    # все батареи, со сводкой (около 15 секунд)
    python tests/run_all.py marks settings     # только батареи, в чьём имени есть эти слова
    python tests/battery_marks.py              # одна батарея напрямую, с подробным выводом
    python -m unittest tests.test_batteries -v # то же через unittest
    python tests/coverage_report.py            # какие строки кода проверки выполняют (1–2 минуты)

Код возврата 0 — всё прошло. Нужны только пакеты самого проекта (numpy, python-docx);
`pypdf` и `scikit-learn` — по возможности: без них часть проверок упрощается или
пропускается (PDF в склейке файлов, настоящие PCA/t-SNE).

## Как это устроено

- **Батарея** — файл `tests/battery_*.py`: последовательность `check("что проверяем", условие)`.
  Каждая запускается в СВОЁМ процессе, потому что подменяет модули (tkinter, messagebox,
  пути в `config`...), и в одном процессе они мешали бы друг другу.
- **Окон нет.** `tests/env.py` подставляет вместо tkinter заглушку `tests/fake_tk`, а вместо
  `keyboard`/`pyperclip` — `tests/fake_libs`: проверки идут быстро, без экрана и не
  перехватывают настоящие клавиши.
- **Окно целиком.** `battery_window_assembly.py` собирает настоящий `AppWindow` на заглушке и
  подставном движке (без данных): это сквозная проверка проводки — кнопки, сервисы, колбэки. Для неё
  в заглушке есть необязательный универсальный режим (`tkinter._GENERIC_FALLBACK = True`): любой
  неизвестный виджет становится безвредной пустышкой. Остальные батареи его не включают и остаются
  строгими. `battery_architecture.py` охраняет границу между окном и контроллером визуализаций.
- **Структура окна — по записи.** `tests/ui_trace.py` строит настоящее окно под заглушкой tkinter и записывает каждое
  обращение к виджетам (создание, настройки, упаковка, привязки, пункты меню). Батарея `ui_layout` проверяет по этой записи,
  что в какой зоне лежит и что делает каждая кнопка; тот же помощник позволяет сравнить две версии кода построения окна
  событие в событие (так проверялся рефакторинг `_create_widgets`).
- **Сервера Manticore нет.** `tests/fake_manticore.py` — небольшой «SQL-сервер» в памяти: понимает ровно те запросы, что
  отправляет движок, и умеет отказывать по заданию; тесты видят, что реально записано в таблицы.
- **Внешние программы не запускаются.** `env.py` ставит предохранитель: если код проекта или
  самой проверки вызывает `os.startfile`, `subprocess`, `os.system` или `webbrowser`, вместо
  запуска будет ошибка, а батарея получит строку `FAIL ...` (даже если код проекта поймал
  исключение и промолчал). Проверка, которой запуск нужен, подменяет его сама, например
  `os.startfile = lambda path: launched.append(path)`. Сторонние библиотеки предохранитель не
  трогает. Поводом стал случай, когда проверка на Windows по-настоящему открыла Блокнот.
- **Известные ошибки.** Если проверка нашла настоящую ошибку в коде проекта, но чинить её решено отдельно, её
  можно оформить как `known_issue(...)` (небольшая функция в самой батарее: при невыполнении условия печатает
  строку «ИЗВЕСТНАЯ ОШИБКА» и не ломает прогон; `run_all.py` собирает такие строки в конце сводки). **Как только ошибку
  исправили, проверку надо превратить в обычную `check(...)`**: `known_issue` прогон не ломает, поэтому
  возврат уже исправленной ошибки остался бы незамеченным (это обнаружилось при проверке тестов намеренными
  поломками). Сейчас все найденные ошибки исправлены, и все такие проверки — обычные.
- **Дымовая проверка на настоящем Tk** (`python tests/smoke_real_tk.py`, нужен экран; в `run_all.py` не входит).
  Остальные батареи идут на подставном Tk и не видят ошибок, возможных только с настоящими виджетами. Скрипт
  собирает настоящее окно, нажимает основные кнопки, выполняет поиск и рисует все визуализации на настоящем
  Canvas, включая цепочку «клик по слову → новый уровень → Назад». Данные пишутся во временную папку.
  Режим `--fake` прогоняет только оконную часть скрипта на подставном Tk (для разработки).
- **Что считается исходниками проекта** (`tests/sources.py`): `.py` в корне и в пакетах верхнего
  уровня (папках с `__init__.py`). Виртуальное окружение `.venv` внутри проекта, `DB`,
  `Manticore`, `build` под это правило не попадают, и проверки их не читают.
- **Данные** — `tests/data/`: ini-файлы настроек с «золотыми» результатами (`*.expected.json`,
  `*.saved.ini` получены прежней реализацией до перехода на `Settings`) и файлы для проверки
  склейки (`merger_src`). Батареи работают с копиями во временных папках — данные не меняются.
- **Добавить батарею:** скопируйте любую `battery_*.py` (первые строки с `env` оставьте),
  напишите проверки — `run_all.py` и `test_batteries.py` найдут её сами. Архивация при запуске
  (`sp.py`) копирует папку `tests/` целиком и ВСЕ исходники проекта автоматически (правило — в
  `utils/project_files.py`), поэтому ни новые проверки, ни новые модули вносить в список вручную не нужно.

## Что защищено, а что нет

Проверки писались вместе с последними доработками, поэтому новые функции покрыты хорошо
(настройки, подчёркивание, ключевые понятия, пароль, нумератор, подсказки, склейка файлов,
режим `**`, архивация). **Ядро поиска и индексации почти не покрыто**: запросы и движки
(Manticore, FTS5, Elastic), разбор запроса (`utils/query_parser.py`), разбиение текста на
топики (`utils/text_processing.py`), индексация файлов, обучение и поиск векторных моделей,
большая часть `SearchController` и `AppWindow`. Точные цифры даёт `coverage_report.py`.
Перед тем как менять эти места, сначала добавьте для них проверки — самое дешёвое начало
это чистые функции `query_parser` и `text_processing`.

## Известные ограничения

- Писались и отлаживались на Linux; на Windows запускались разработчиком (первый запуск нашёл три
  ошибки самих проверок — они исправлены). Что именно ведёт себя по-разному на ОС (способ
  открытия файла), проверяется в обеих ветках на любой машине.
- Заглушка tkinter не рисует: внешний вид окон и реальное поведение Tk (фокус, события
  мыши, размеры кнопок) проверками не покрыты.
